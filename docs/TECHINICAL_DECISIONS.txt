# Uso de TypeScript com OOP Estrita

- Contexto: O projeto exige alta qualidade de código, manutenibilidade, e possuo familiaridade com a linguagem
- Decisão: Adotarei TS tanto no front quanto no back
- Justificativa: Ajuda na previsibilidade, facilita a modelagem do domínio (exemplo: periodico, AreaAvaliacao) e reduz erros em tempo de execução



# Estratégia de versionamento (git flow simplificado)

- Contexto: O projeto precisa de um histórico limpo e organizado, separando código em desenvolvimento 
de código pronto para produção.
- Decisão: Adotarei duas branches principais: main (código estável/produção) e develop (integração), novas funcionalidades sairão de develop (ex: feat/database-setup).
- Justificativa: Evita quebrar a aplicação principal durante minha construção, facilita o code review e demonstra boas práticas de CI/CD e trabalho



# ORM e DB (Prisma + SQLite)

- Contexto: O projeto precisa de um banco de dados relacional e de uma forma segura de interagir com ele via código, assim  não sera necessario instalar serviços para rodar o projeto (como Postgres).
- Decisão: Adotei o SQLite como banco físico e o Prisma ORM para a comunicação 
# ------------------------------------------------------------------------------------------------------  
  Adicionei @@index nas colunas issn e titulo pois como a base da CAPES é grande e o requisito (RF03) é buscar por esses campos, os índices garantirão que a busca seja EXTREMAMENTE rapida
# ------------------------------------------------------------------------------------------------------
- Justificativa: O SQLite reside em um único arquivo local (portabilidade extrema). O Prisma integra perfeitamente com TypeScript, entregando tipagem estrita desde a consulta no banco até a resposta da API.

- Dei downgroad no prisma para a versão (5v) por erros de configuração. nota: A nova estrutura do prisma.config.ts era uma complexidade desnecessária para este projeto com SQLite



# Padrão repository e processamento de arquivos

- Contexto: Preciso inserir milhares de dados do CSV da CAPES no banco de dados sem acoplar a lógica de persistência diretamente nos scripts ou rotas.
- Decisão: Implementei o *Repository Pattern* "PeriodicoRepository" seguindo OOP para o CSV, usei a biblioteca "csv-parser" e processamento em *Streams* pra carregar em lotes.
- Justificativa: Segundo algumas pesquisas, o padrão repository blinda a aplicação contra mudanças no ORM portanto usar streams e lotes inserindo de 5000 em 5000 evita estouro de memória na leitura do CSV, 
isso deixa o processo seguro e performático independente do tamanho da base



# Construção da API REST (Express + Orientação a Objetos)

- Contexto: Era preciso expor os 171.111 registros do banco de dados para consumo do front, para performance através de paginação e os filtros
- Decisão: Utilizei express.js estruturado com TS, criei as classes "Server" para inicialização e rotas e "PeriodicoController" para lidar com as requisições
adotei a injeção de dependência, passando o "PeriodicoRepository" para o Controller via construtor
- Justificativa: A injeção de dependência (princípio da inversão de dependência do SOLID) desacopla a camada HTTP da camada de banco de dados, deixando o código testável 
e manutenível

- Contexto: Precisava centralizar toda comunicação HTTP com o backend e evitar código duplicado nos componentes

- listarAreas(): busca lista de áreas únicas
- buscarPeriodicos(): busca periodicos com filtros e paginação
- obterEstatisticas(): busca distribuição por estrato

- Justificativa: desacoplar os componentes da implementação específica da API

# Custom hooks para estado e side effects

- Contexto: Componentes precisam gerenciar estado assíncrono, loading states e tratamento de erros de forma clean
- Justificativa: eles encapsulam lógicas muito complexas e efeitos colaterais, os componentes ficam mais clean e focados na exibição

# Interface de busca facetada 

- Contexto: O requisito pedia filtros intuitivos por área, estrato e termo de busca, me inspirei no SCImago Journal Rank, eu foquei 
em fazer uma UX superior à plataforma sucupira original
- Decisão: Implementei um faceted search com campo de busca textual para título/ISSN, dropdown para a área de avaliação, botões para os estratos e um botão contextual pra limpar filtros
- Justificativa: Pesquisando, exnontrei um padrão de mercado para filtros complexos (usado por amazon, google scholar, etc). Cada filtro é independente e pode ser combinado

# Tabela de dados com performance

- Contexto: era necessário mostrar milhares de registros em uma tabela sem engasgar o navegador
- Decisão: Implementei a paginação diretamente no backend trazendo somente 20 registros por página, criei loading states (spinner/skeleton) durante o carregamento, empty states com mensagens claras quando
nao obtivera resultado
- Justificativa: é essencial para a performance; tentar renderizar 171k linhas no DOM seria inviável. os estados de loading e empty melhoram drasticamente a UX pois o user nunca fica olhando para uma tela em branco sem saber o que aconteceu

# Visualização de estatísticas (EM DESENVOLVIMENTO)

- Contexto: O requisito pedia para "visualizar a distribuição" dos periódicos, eu precisava de algo mais dinâmico e interessante do que apenas uma tabela de totais
- Decisão: Estou arquitetando um design onde utilizo barras horizontais (com animaçao) com largura proporcional representando a % do total, usando a mesma paleta de cores dos botões de filtro
 também implementei cards de resumo mostrando o total de periódicos dos estratos A contra os da base B
- Justificativa: Barras horizontais são muito mais legíveis que gráficos de pizza pra comparar múltiplas categorias. 
A animação via CSS (implementando a partir de tutoriais) deixou um polimento profissional e como fiz nativamente não precisei instalar bibliotecas pesadas como o chart.js, mantendo o bundle leve

# Sistema de abas (tabs)

- Contexto: precisava de uma forma de alternar entre a tabela de dados e o gráfico de estatísticas sem poluir a tela
- Decisão: Implementei um componente de tabs que gerencia a navegação entre a aba "periódicos" (tabela) e "estatísticas" (gráficos).

# Design system e paleta de cores

- Contexto: Eu precisava de uma paleta de cores que fosse visualmente atraente, acessível e diferente do clichê padrão
- Decisão: Adotei um gradient system baseado em cores frias e neutras, 
  Estratos A (excelentes) vão do verde-esmeralda até o azul-céu (do tailwind); 
  Estratos B (bons) vão do azul até tons mais neutros como cinza; 
  Estrato C (baixo) fica em vermelho, o background principal usa um gradient de cinza
- Justificativa: A progressão cromática de verde pra vermelho é universalmente compreendida e cores frias transmitem o profissionalismo pra um sistema acadêmico, 
o uso do tailwindCSS da consistência em toda a aplicação

 mensagens quando não há resultados e adicionei hover effects em cada linha
- Justificativa: A paginação backend-side é bom pra performance; 
tentar renderizar 171k linhas no DOM seria inviável

# Responsividade e Mobile-First

- Decisão: implementei um grid responsivo no mobile (< 1024px), os filtros ficam empilhados acima da tabela; no desktop eles vão para uma barra lateral esquerda fixa. 
adicionei tratamento de overflow pra a tabela ter scroll horizontal no celular
- Justificativa: usar a grid do tailwind deixou uma adaptação fluida sem quebrar o layout

# Estados de interface

- Contexto: Aplicações lidam com latência de rede, falhas no servidor ou buscas que não retornam nada
- Decisão: mapeei e implementei 3 estados vitais em cada componente: 
loading (indicador visual + "Carregando..."), 
Empty (svg de pasta vazia + instrução) 
Error (tratamento de falhas via hook)

# Otimização de renderização

- Contexto: re-renderizações desnecessárias da árvore de componentes poderiam obstruir a experiência e deixar a digitação dos filtros lenta
- Decisão: utilizei "useCallback" pra memorizar funções passadas via props, implementei "useEffect" com dependências definidas
pra sincronizar dados com a API, e usei renderização condicional
- Justificativa: O "useCallback" evita que componentes filhos como paginação ou a própria tabela re-renderizem atoa
